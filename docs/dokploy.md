# Запуск в Dokploy

Используйте **Docker Compose**, файл `compose.dokploy.yml` в корне репозитория. Он запускает `web` (Apache/PHP + Node SSR) и MariaDB 11.8. Данные БД и uploads хранятся в отдельных именованных томах.

## Перед первым запуском

1. Запустите `npm ci` и `npm run build` локально. Добавьте в коммит все обновлённые, новые и удалённые файлы клиентской и SSR-сборки. Docker использует эти артефакты; npm на сервере не запускается.
2. В Dokploy создайте Compose-сервис, выберите репозиторий/ветку и путь `./compose.dokploy.yml`.
3. Заполните **Environment** по `docker/dokploy.env.example`: публичный `WP_URL` с HTTPS, пароли БД, восемь уникальных ключей/солей, `COMPOSER_AUTH`. В репозиторий реальные значения не добавляйте.
4. Для `COMPOSER_AUTH` нужен JSON с доступом GitHub к закрытым зависимостям и лицензией ACF PRO. Он передаётся только как BuildKit secret; в окружение работающего web-контейнера не попадает. GitHub-доступ к самому репозиторию приложения настраивается отдельно в Dokploy.
5. В **Domains** добавьте домен к сервису `web`, container port **80**, включите HTTPS. Host ports для web/БД и порт SSR **13714** публиковать не нужно. Dokploy добавляет сетевые настройки и Traefik labels при деплое.
6. Выполните Deploy. Образы используют Node 24 и PHP 8.5. `web` ждёт готовности БД, затем запускает Apache и SSR. Healthcheck проверяет оба процесса через HTTP.

Получить случайное значение для каждого пароля/соли можно командой `openssl rand -hex 32`. При переносе существующего сайта допустимо сохранить его уникальные соли, чтобы не сбрасывать сессии.

## Данные и миграция

- Для существующей БД задайте её реальный `DB_PREFIX` до запуска. Импортируйте БД и uploads через штатные средства переноса/Syncport; выполните замену старого домена с учётом сериализованных данных.
- Compose не копирует локальную БД и uploads, не создаёт администратора и не запускает миграцию автоматически.
- На чистой БД завершите установку WordPress, активируйте ACF PRO, Inertia WordPress, WP Vite и нужные плагины; jD Support загружается как MU-plugin. Для существующей БД активации сохраняются при импорте.
- Не монтируйте том поверх всего `/var/www/html` или `wp-content`: это скроет код новой версии. Постоянный файловый том предназначен для `wp-content/uploads`.
- Настройте резервные копии MariaDB и uploads в Dokploy. Не удаляйте эти тома при обычном редеплое. Смена имени Compose-проекта создаст другие именованные тома.
- Языковые пакеты и прочие файлы, устанавливаемые вне Composer, нужно учитывать отдельно при миграции; контейнер не включает произвольные локальные плагины.

## Проверка после запуска

- `GET /healthz` должен вернуть `ok`; Docker health status — `healthy`.
- Главная и внутренняя страница должны открываться без dev-server URL. В исходном HTML внутри `#app` должен быть серверный контент.
- Проверьте загрузку изображения, форму и доставку почты после настройки SMTP для целевого домена. Production отправку почты локальный тест не выполняет.
- `INERTIA_SSR_ENABLED=1` и `INERTIA_SSR_PORT=13714` синхронизируют Node и настройки Inertia через MU-plugin, без правок БД. Для отключения SSR поменяйте значение в Compose на `0` и выполните редеплой.
- Если Apache или SSR завершится, entrypoint остановит второй процесс, а restart policy перезапустит контейнер. Healthcheck сам по себе не перезапускает зависший процесс — для этого используйте мониторинг Dokploy.
- Обновление кода/плагинов выполняется через Composer и новый образ, не через редактирование файлов в админке.

## Локальная проверка Docker

```sh
docker build --secret id=composer_auth,src="$HOME/.composer/auth.json" -t wordpress-starter:production .
```

Для проверки Compose используйте отдельный файл окружения с тестовыми значениями:

```sh
docker compose --env-file /path/to/test.env -f compose.dokploy.yml config --quiet
docker compose --env-file /path/to/test.env -f compose.dokploy.yml build
```

Не публикуйте вывод `docker compose config` без `--quiet`: он содержит подставленные пароли.
