# Установка WordPress-стартера на сервер без Docker

WordPress работает под PHP-FPM с Apache или Nginx. MariaDB или MySQL могут находиться на этом же сервере либо на отдельном хосте. Node.js 26 LTS нужен на
сервере при запуске SSR. Для сайта без SSR достаточно заранее подготовленных клиентских ассетов.

## Подготовка

1. Разместите проект, например, в `/srv/www/example.com`. Используйте PHP 8.5 или совместимую версию от 8.4.1 и расширения, которые требуют Composer и
   WordPress, включая `mysqli`.
2. Укажите `WP_ENV=production`, `ENV_PRODUCTION=https://example.com`, параметры БД и уникальные соли в `.env`. Файл можно хранить на уровень выше каталога
   проекта. PHP-пользователю нужен доступ на чтение. При переносе сохраните фактический `DB_PREFIX`.
3. Настройте авторизацию Composer для ACF PRO и приватных зависимостей. В каталоге проекта выполните `composer install --no-dev --no-interaction`. Composer
   размещает ядро WordPress и плагины по путям проекта. Проверьте зависимости через `composer check-platform-reqs --no-dev`.
4. Выполните `npm ci` и `npm run build` на Node.js 26 локально, в CI или на сервере. Перед сборкой задайте `VITE_PRIMEUI_LICENSE` в `.env` в корне проекта или в
   окружении процесса сборки. Передайте каталог клиентской сборки `wp-content/themes/inertia/resources/Public/Build/` и для SSR каталог
   `wp-content/themes/inertia/resources/Private/.vite/ssr/` вместе с соответствующей версией PHP-кода. Git стартера хранит исходники, а оба каталога сборки
   передаются как артефакты деплоя.
5. PHP-пользователю нужны права записи в `wp-content/uploads` и `wp-content/themes/inertia/.inertia`. Предварительно создайте эти каталоги. Настройки и код
   оставьте доступными PHP на чтение.

## Виртуальный хост

В обоих шаблонах уже подключена защита служебных путей.

- [Apache + PHP-FPM](../server/apache/site.conf.example) использует модули `ssl`, `alias`, `rewrite`, `headers`, `proxy` и `proxy_fcgi`.
- [Nginx + PHP-FPM](../server/nginx/site.conf.example) пропускает запросы к PHP в FPM только для существующих файлов.

Подставьте домен, абсолютный путь к проекту, сокет PHP-FPM и пути к TLS-сертификату. Включите виртуальный хост в системной конфигурации и настройте HTTP → HTTPS
для этого домена. При использовании Nginx как прокси перед Apache передавайте запросы в Apache, где действует тот же набор ограничений. На управляемом хостинге
правила должны быть подключены к активному виртуальному хосту через панель или администратора хостинга.

Перед перезагрузкой проверьте конфигурацию командой `apachectl -t` или `nginx -t`. После включения сайта запустите проверку публичных путей.

```sh
sh scripts/checks/public-paths.sh https://example.com
```

Служебные пути должны возвращать 404 со страницей ошибки темы. Главная и логотип должны возвращать 200. Обновите путь к логотипу в проверке, если производный
проект использует другой публичный ассет.

## SSR на том же сервере

В `.env` задайте `INERTIA_SSR_ENABLED=1`. Если порт не указан, PHP и Node используют `13714`. Для другого порта задайте `INERTIA_SSR_PORT` в `.env` для PHP и в
окружении процесса PM2 для Node.

С установленными npm-зависимостями запустите `npm run ssr` под пользователем проекта. PM2 запускает Node напрямую. Проверьте SSR через
`curl --fail http://127.0.0.1:13714/health` и настройте автозапуск PM2 в системном менеджере служб. Оставьте порт SSR на loopback. При выключенном SSR WordPress
отдаёт HTML с данными для клиентского рендера.
